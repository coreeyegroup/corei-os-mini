# Audit — 14 Nov 2026 (release 0.26.0)

Scope: the end-to-end flow (connect → prices → strategy → portfolio → orders), technology, architecture,
code structure and screen design. Status words: **FIXED** in this release, **OPEN** with owner.

## 1. MT5 servers and accounts (owner's question)

**Finding.** The 0.25.0 tree put an MT5 *server* between the broker and its accounts. A broker such as
VT Markets, IC Markets or MetaQuotes publishes many servers and access points (MetaQuotes-Demo alone lists
about 50 access points), and the best one changes with latency, so a person adding servers by hand does not scale.

**How MT5 actually works.** Two different things are both called "servers":

| | What it is | Who decides | How many |
| --- | --- | --- | --- |
| **Server name** (e.g. `VTMarkets-Live 3`) | The trade server that holds the login | The broker, when the account is opened | One per login. Brokers have several (Live 1…Live 30), each holding different logins |
| **Access point** (e.g. `198.51.100.10:443`) | An address in front of that trade server | COREI may choose | Many per server name; the fastest varies by location and hour |

A login works only on its own server name, but on any of that server's access points. So the server name
is a fact *of the account*, and the access point is a *choice* made per account, by latency.

**FIXED (0.26.0).**
- Tree: **MetaTrader 5 › broker › accounts**. Each account line shows its server name and the latency of the
  address it uses first. No server level, and nobody adds MT5 servers by hand: the server record is kept
  automatically from the accounts (created when the first account on a server is added).
- **Add who** under MetaTrader 5 asks only for the broker and goes straight to *Add MT5 account*, where the
  server is picked from the broker's published list (MT5 broker directory or a servers.dat).
- Each MT5 account has **Server & route**:
  - **Fastest (automatic)**, now the default for new accounts: the server's addresses, fastest first.
    COREI measures them again automatically **every 6 hours and before each login** (broker reads and
    collector start), so the order follows the network without anyone pressing a button.
  - **Server's order** or **Pinned** (the account's own list and order) remain.
  - **Measure now**, **Refresh from broker** (adds addresses the broker now publishes, measures them, reports
    addresses no longer published; LIVE additions go to approval) and **Change server…** (pick another server
    of the same broker from its published list; the account keeps its id, password, groups and history; a
    demo login cannot move to a live server; LIVE moves need approval).
- API: `POST /api/config/accounts/{id}/mt5-latency`, `…/mt5-addresses/refresh`, `…/mt5-server`.

## 2. Flow, end to end

| Stage | State | Gap |
| --- | --- | --- |
| Connect (technology › who › accounts) | Built: MT5 direct + bridge, FIX 4.4/4.2, Upstox | MT4, cTrader, native fast feeds and exchange-direct are planned |
| Prices (collector, journal, quality, bars, archive) | Built | MT5 direct blocked by the out-of-date mtapi SDK (A-31) |
| Strategy → signal | **Paper only**: `workflow.run_paper_workflow` on synthetic prices | Not yet fed by collected prices (A-34) |
| Portfolio allocation and risk | Built as pure functions (`allocation.py`, `risk.py`, `order_checks.py`) | Run only in the paper workflow (A-34) |
| Orders to accounts | **Not built** | No order adapter for MT5, FIX or Upstox (A-32) |
| Fills, positions, P&L reconciliation | Not built | Follows order adapters (A-35) |

The platform today is a reliable **connectivity and market-data system with a paper decision engine**.
The next value is wiring collected prices into the strategy engine (paper first), then order adapters.

## 3. Technology

- **MT5 direct (mtapi SDK).** Professional route (same libraries as Westernpips), but COREI's copy is older
  than the brokers' servers (1035; failure after login). **OPEN, owner:** current licence with updates (A-31).
- **MT5 terminal bridge.** Works with any build, one login per terminal; kept as fallback.
- **FIX 4.4/4.2.** Market data built and tested against a simulated venue; not yet tested against a real venue.
- **Upstox.** Built; the last owner login was refused (Cloudflare suspected for a non-Indian egress IP).
- **Latency.** TCP connect time from the COREI server; public addresses only; history kept per address.

## 4. Architecture

- Clear layers: records (`config_store`) › adapters (`md/*_reader`, `broker_session`) › collector › storage
  (PostgreSQL ticks + Parquet archive + DuckDB) › workstation UI. One line protocol for every reader.
- Four-eyes on everything that changes where LIVE credentials go (addresses, servers, connections).
- **Risk:** strategy, allocation and risk are not yet connected to live prices (A-34).
- **Risk:** the collector runs as one service; no second node (single point of failure for prices) (A-36).

## 5. Code structure

- `ui/src/Configuration.tsx` is 1,750 lines and `config_store.py` 1,100+ lines. They work and are tested,
  but should be split by domain (accounts, connections, MT5 setup, credentials) before order adapters land (A-37).
- The UI bundle is 555 kB in one chunk; split the workstation into lazily loaded screens (A-38).
- Tests: backend 104, UI 34, CI green. A date-dependent test (expiry on a fixed date) was found and made relative.

## 6. Design

- Dense VS Code style kept. The route-mode cards are tall; a compact selector could save space (low).
